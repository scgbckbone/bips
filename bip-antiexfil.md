## Abstract

This BIP specifies a two-round *anti-exfil* (also known as *anti-klepto* or *sign-to-contract*) signing protocol for hardware and air-gapped Bitcoin signers. A host device contributes entropy that the signer is provably forced to fold into its signing nonce, removing the signer's freedom to choose the nonce and thereby closing the covert channel through which a compromised or malicious signer could otherwise leak the private key bit by bit across signatures.

The construction is specified normatively for both **ECDSA** inputs (legacy and segregated-witness v0) and **Taproot / BIP-340 Schnorr** inputs (key path and script path). It also defines the per-input PSBT fields (first-class keytypes, assigned here) required to run the protocol across an air-gap.

## Motivation

A hardware signer that knows the private key can leak it through its choice of signing nonce, without producing a signature that looks invalid to anyone. The classic attack: the signer encodes a few bits of the secret key into each nonce it picks (for example by grinding the nonce until some function of `R` equals the next chunk of the key); a passive observer who knows the scheme then recovers the full key after a handful of on-chain signatures. Determinism (RFC 6979) does not help — a malicious signer simply ignores it, and an observer cannot tell a deterministic nonce from an adversarial one by looking at the signature.

The defence is to deny the signer sole control of the nonce. A second device (the *host*) supplies 32 bytes of entropy `rho` that the signer must incorporate into its nonce in a way the host can verify after the fact. Crucially, the protocol is ordered so neither party can adapt to the other: the host commits to `rho` before it learns the signer's nonce point, and the signer commits to its nonce point before it learns `rho`. The final nonce is then a function of both contributions and is unpredictable to the signer at commit time, so there is no nonce freedom left to exfiltrate through.

This is the same *sign-to-contract* class of construction implemented by Blockstream's libsecp256k1 `anti_exfil` module. This document specifies the construction normatively and defines the PSBT carriage needed to run it over an air-gap where the host and signer exchange files rather than an interactive session.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119.

### Notation and primitives

* The curve is secp256k1 with generator `G` and order
  `n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141`.
* `*` is EC scalar multiplication / scalar multiply, `||` is byte concatenation, `mod n` reduces modulo the curve order, and `x(P)` is the affine x-coordinate of point `P`.
* `tagged_sha256(tag, msg) = SHA256( SHA256(tag) || SHA256(tag) || msg )`, the tagged hash of BIP-340. As in BIP-340, each `tag` is an arbitrary-length byte string; the tags used here are the exact variable-length ASCII strings given in [Tags](#tags), hashed as-is with no padding or length normalization.
* `rho` is the 32-byte host entropy. It MUST be freshly generated by a cryptographically secure RNG for every new protocol instance (see [Security Considerations](#security-considerations) for the reuse rules).
* "**digest**" is the 32-byte sighash of the input being signed:
  * ECDSA: the legacy or BIP-143 segwit-v0 double-SHA256 sighash for the sighash type being signed.
  * Taproot: the BIP-341 signature hash (`hash_TapSighash`) for the actual sighash type being signed — SIGHASH_DEFAULT only when no explicit type is requested — with the BIP-342 tapscript message extension for a script-path spend.

### Tags and nonce derivation

Four tagged-hash domains are used. They are distinct and MUST NOT be interchanged:

| Constant | Value (ASCII) | Role | Interop-critical? |
|---|---|---|---|
| `HOST_COMMITMENT_TAG` | `s2c/ecdsa/data` | hashes `rho` to form the host commitment, ECDSA inputs | host and signer must agree |
| `ECDSA_TWEAK_TAG` | `s2c/ecdsa/point` | binds the final ECDSA nonce to `Q` and `rho` | **yes — must match across signer and every verifier** |
| `SCHNORR_HOST_COMMITMENT_TAG` | `s2c/schnorr/data` | hashes `rho` to form the host commitment, Schnorr inputs | host and signer must agree |
| `SCHNORR_TWEAK_TAG` | `s2c/schnorr/point` | binds the final Schnorr nonce to `Q` and `rho` | **yes — must match across signer and every verifier** |

The two ECDSA tags are the values deployed in the libsecp256k1-zkp `anti_exfil` module: the ECDSA wire format of this BIP is byte-for-byte compatible with it (see [Rationale](#rationale)). The Schnorr tags mirror the same naming scheme with `schnorr` in place of `ecdsa`; the Schnorr construction has no deployed format to match, so these values are defined by this BIP and are final. Giving each scheme its own host-commitment domain is deliberate domain separation, not a compatibility requirement — the commitment only binds `rho`.

Neither scheme needs a BIP-specific nonce-derivation tag: the ECDSA derivation is the standard **RFC 6979** HMAC-SHA256 function with `host_commitment` as extra entropy (exactly as libsecp256k1's default nonce function applies it), and the Schnorr derivation is the standard **BIP-340** nonce derivation with `host_commitment` as auxiliary data. A nonce-derivation function affects only the determinism of a single signer's own nonce, so its exact form is not interop-critical — but the ECDSA/Schnorr separation that these two standard functions provide is NOT optional: sharing `q` across ECDSA and Schnorr signatures over the same `(sk, digest, host_commitment)` is key-recoverable (see [Security Considerations](#security-considerations)).

### Construction A — ECDSA inputs (normative)

Let `sk` be the 32-byte signing scalar and let the signer public key be the 33-byte compressed SEC1 encoding of `sk*G`.

**Round 1 (host commits, signer pre-commits):**

1. The host generates `rho` freshly for this protocol instance: it MUST come from a cryptographically secure RNG, MUST be unpredictable to the signer, and MUST NOT be reused for any other transaction, input, or signer (the sole exception is the same-transaction, same-`Q` retry described in [Security Considerations](#security-considerations)). The host computes `host_commitment = tagged_sha256(HOST_COMMITMENT_TAG, rho)` (32 bytes) and sends it to the signer. The host keeps `rho` secret for now.
2. The signer derives a deterministic secret nonce `q` with **RFC 6979** (HMAC-SHA256 DRBG) exactly as libsecp256k1's default nonce function does: the DRBG is keyed with `sk || digest || host_commitment` (raw 32-byte strings, in this order; no `bits2octets` conversion, no algorithm identifier), and candidate `counter = 0, 1, 2, ...` is the `counter`-th 32-byte DRBG output block, taking the first candidate with `1 <= q < n`. (Deterministic derivation is REQUIRED for a stateless air-gapped signer — one that keeps no state between rounds cannot otherwise reproduce its round-1 `Q` in round 2. A signer that instead uses a random `q` MUST persist `q`/`Q` between rounds.)

3. The signer computes `Q = q*G` and encodes it as a **33-byte compressed SEC1 point with its natural parity** (`0x02`/`0x03` prefix). `Q` is the *signer_commitment*. The signer MUST NOT apply any even-y / x-only normalization to the ECDSA `Q`.
4. The signer returns `Q` and adds **no** signature.

**Round 2 (host reveals `rho`, signer signs):**

1. The host sends `rho`.
2. The signer MUST verify `tagged_sha256(HOST_COMMITMENT_TAG, rho) == host_commitment`; otherwise it MUST abort.
3. The signer re-derives `q` and `Q` from the same `digest` and `host_commitment` and MUST verify that `Q` equals the `Q` it returned in round 1; otherwise it MUST abort.
4. Compute the tweak and the bound nonce:

   ```
   tweak = tagged_sha256(ECDSA_TWEAK_TAG, Q33 || rho)      # Q33 = 33-byte compressed Q
   k     = (q + tweak) mod n
   ```

   If `k == 0` (probability ~2^-128), the signer MUST abort; it MUST NOT sign with a zero nonce.

5. Produce an ECDSA signature over `digest` using nonce `k`. The signer MUST enforce low-S (BIP-146) and MUST NOT perform low-R grinding (the nonce is forced and cannot be ground).

**Offline verification** (performed by the host or any later verifier that holds `Q` and `rho`):

```
tweak = tagged_sha256(ECDSA_TWEAK_TAG, Q33 || rho)
R     = Q + tweak*G
require x(R) mod n == r                       # r is the signature's r value
require ECDSA-Verify((r, s), digest, signer_pubkey)
```

The `Q` used here MUST be the exact value the host received in round 1, retained independently of any PSBT returned by the signer — see the pinning requirement in [Air-gap flow](#air-gap-flow). A binding computed against a `Q` taken from the signer's round-2 output proves nothing, because the signer could have chosen that `Q` after learning `rho`.

Both checks MUST pass. The first check is what proves the published `r` was bound to the committed `Q` and to the host's `rho`; the second is an ordinary ECDSA verification.

### Construction B — Taproot / BIP-340 Schnorr inputs (normative)

Let `sk` be the scalar actually used to sign:

* key path: the private key after the BIP-341 output-key tweak (i.e. the scalar whose `x`-only public key is the taproot output key);
* script path: the tapscript private key.

The signer public key is 32-byte x-only. The signing API is handed the secret key (or keypair); the BIP-340 even-y normalization of the *signing key* is internal to the signer and is independent of the steps below.

**Round 1:**

1. `host_commitment = tagged_sha256(SCHNORR_HOST_COMMITMENT_TAG, rho)`, sent to the signer. The freshness requirements on `rho` from Construction A apply unchanged.
2. The signer derives a deterministic secret nonce `q` with the **BIP-340 nonce derivation**, using `host_commitment` as the auxiliary data in place of BIP-340's `aux_rand`:

   ```
   t = bytes(d) XOR tagged_sha256("BIP0340/aux", host_commitment)   # d = even-y-adjusted signing scalar
   q = int(tagged_sha256("BIP0340/nonce", t || pubkey_x || digest)) mod n
   ```

   If `q == 0` (probability ~2^-128), the signer MUST abort. Using the BIP-340 derivation — a function that differs from Construction A's RFC 6979 derivation in every input and domain — is mandatory: sharing `q` across an ECDSA and a Schnorr signature over the same `(sk, digest, host_commitment)` leaks the private key (see [Security Considerations](#security-considerations)). The same statelessness considerations as in Construction A apply.
3. Compute `q*G`. **If `q*G` has odd y, set `q = n - q`** so that `Q` is even-y. Let `Q = x-only(q*G)`, a 32-byte value. This is the *signer_commitment*.
4. The signer returns `Q` (32 bytes) and adds **no** signature.

**Round 2:**

1. The signer MUST verify `host_commitment` opens to `rho`, and MUST reproduce the identical `Q`; otherwise it MUST abort.
2. Compute:

   ```
   tweak = tagged_sha256(SCHNORR_TWEAK_TAG, Q32 || rho)      # Q32 = 32-byte x-only Q
   k     = (q + tweak) mod n                                 # q is the even-y-adjusted nonce scalar
   ```

   If `k == 0` (probability ~2^-128), the signer MUST abort; it MUST NOT sign with a zero nonce.

3. Produce a BIP-340 signature over the 32-byte message `digest` using nonce `k` exactly as computed above. The nonce is fully determined by the protocol: the auxiliary data of the derivation is `host_commitment`, and the signer MUST NOT mix in any other entropy on top of `k` — doing so reintroduces signer nonce freedom and breaks the binding. A BIP-340 signer internally negates the nonce (`k = n - k`) if `k*G` has odd y, to satisfy the even-`R` rule. **This internal negation does not affect the binding**, which is on the x-coordinate of `R` only.
4. The 64-byte signature is `(R_x, s)`; the *signer_commitment* `Q` remains the 32-byte x-only value from round 1.

This applies to **both**:

* **key-path** spends — one signature per input, signer pubkey = the 32-byte taproot output key; and
* **script-path** spends — one signature per `(x-only key, leaf hash)` pair, exactly as a tapscript signature is keyed.

**Offline verification:**

```
P = lift_x(Q)                                 # the even-y point with x-coordinate Q
R = P + tweak*G
require sig.R_x == x(R)
require BIP340-Verify(signer_pubkey, digest, sig)
```

As in Construction A, the `Q` used here MUST be the round-1 value pinned by the host, not a value taken from the signer's round-2 output.

Because only `x(R)` is committed and `x(P) == x(-P)`, the binding check is parity-independent: BIP-340's internal even-`R` negation cannot make it fail.

### PSBT fields

These fields carry the protocol state across the air-gap. **All fields are per-input** and are keyed by the signing public key so that independent cosigners (e.g. multisig, where each signer produces its own separate signature) carry independent data. This protocol covers independent per-signer signatures only; it does NOT compose with aggregate-nonce schemes such as MuSig2 as-is, which require their own anti-exfil treatment.

Two field *families* are defined with **distinct keytypes**, one for ECDSA and one for Taproot. They are kept separate deliberately: the keydata that disambiguates "which signer / which signature" differs by signature type — a 33-byte compressed key for ECDSA versus a 32-byte x-only key (key path) or x-only key `||` leaf hash (script path) for Taproot, mirroring `PSBT_IN_PARTIAL_SIG` versus `PSBT_IN_TAP_KEY_SIG`/`PSBT_IN_TAP_SCRIPT_SIG`. A single shared keytype could not encode both keydata shapes unambiguously, and the value layout (33-byte vs 32-byte `signer_commitment`) also differs; conflating them would force a verifier to guess the input's signature type from context rather than from the key.

The keytype values below are assigned by this BIP as the first unassigned per-input keytypes: the registry tops out at `0x20` (`PSBT_IN_SP_TWEAK`, BIP-375), so this BIP claims `0x21`–`0x26`. (Check for conflicts at implementation time if other BIPs have since landed.) This encoding is used to produce the test vectors in this document.

**ECDSA family** — keydata = 33-byte compressed signer public key:

| Name | `<keytype>` | `<keydata>` | `<valuedata>` | Description |
|---|---|---|---|---|
| `PSBT_IN_ANTI_EXFIL_HOST_COMMITMENT` | `0x21` | `<33-byte compressed pubkey>` | `<32-byte host_commitment>` | `tagged_sha256(HOST_COMMITMENT_TAG, rho)`, supplied by the host in round 1. |
| `PSBT_IN_ANTI_EXFIL_SIGNER_COMMITMENT` | `0x22` | `<33-byte compressed pubkey>` | `<33-byte compressed Q>` | The signer's nonce point `Q` with natural parity, supplied by the signer in round 1. |
| `PSBT_IN_ANTI_EXFIL_HOST_ENTROPY` | `0x23` | `<33-byte compressed pubkey>` | `<32-byte rho>` | The host entropy `rho`, revealed by the host in round 2. |

**Taproot family** — keydata mirrors BIP-371's keying for the matching signature:

* key path: keydata = 32-byte x-only **output key** (the same key used by `PSBT_IN_TAP_KEY_SIG`-adjacent metadata). This is **decided** to be the x-only output key, **not empty** — it is symmetric with the ECDSA family and with `PSBT_IN_TAP_SCRIPT_SIG`, and keeps multiple signers on one input unambiguous.
* script path: keydata = 32-byte x-only key `||` 32-byte leaf hash, exactly as `PSBT_IN_TAP_SCRIPT_SIG`.

| Name | `<keytype>` | `<keydata>` | `<valuedata>` | Description |
|---|---|---|---|---|
| `PSBT_IN_TAP_ANTI_EXFIL_HOST_COMMITMENT` | `0x24` | `<32-byte x-only output key>` *(key path)* or `<32-byte x-only key> <32-byte leaf hash>` *(script path)* | `<32-byte host_commitment>` | Host commitment to `rho`, round 1. |
| `PSBT_IN_TAP_ANTI_EXFIL_SIGNER_COMMITMENT` | `0x25` | as above | `<32-byte x-only Q>` | The signer's even-y nonce point `Q`, x-only, round 1. |
| `PSBT_IN_TAP_ANTI_EXFIL_HOST_ENTROPY` | `0x26` | as above | `<32-byte rho>` | Host entropy `rho`, round 2. |

### Air-gap flow

The constructions above are transport-agnostic: any channel that can carry the three small messages (`host_commitment`, `Q`, `rho`) can run them. A connected signer (USB, NFC, serial) MAY execute the same two rounds as an interactive session — the libsecp256k1 `anti_exfil` API works exactly this way — without ever serializing a PSBT; the normative steps, the pinning requirement, and the offline verification are identical. The PSBT fields defined above are the carriage for the file-based air-gap case, where the two rounds become two PSBT round-trips (the same shape for ECDSA and Taproot inputs):

1. **Round-1 PSBT (host → signer):** carries `host_commitment` per signer key per input. The signer returns the PSBT with `signer_commitment` added and **no** partial signatures.
2. **Round-2 PSBT (host → signer):** carries `host_commitment` + `signer_commitment` + `host_entropy` (`rho`). The signer verifies the commitments (see Constructions A and B), signs, and returns the PSBT with `PSBT_IN_PARTIAL_SIG` (ECDSA) / `PSBT_IN_TAP_KEY_SIG` (Taproot key path) / `PSBT_IN_TAP_SCRIPT_SIG` (Taproot script path) added. The anti-exfil fields are preserved so a verifier can later check the binding.
3. **Host pinning (mandatory):** the host MUST retain the exact round-1 `host_commitment` and `signer_commitment` values it sent and received, independently of any later PSBT, and MUST reject the round-2 result if any of these values differ from the retained ones. The final PSBT is assembled by the signer, so a host that reads `Q` from it without comparing against the pinned round-1 value has no guarantee that the commitment preceded the reveal of `rho` — a malicious signer could choose `Q` after learning `rho` and fabricate a passing binding (see [Security Considerations](#security-considerations)).
4. **Finalization:** the anti-exfil fields are dropped along with the other PSBT metadata. A verifier that holds only the broadcast transaction therefore MUST retain `Q` and `rho` out-of-band (or from the round PSBTs) to re-check the binding; the binding is not recoverable from the network transaction alone. A third-party verifier that did not itself run round 1 cannot confirm the commitment ordering and only gets a consistency check, not proof of protection — the anti-exfil guarantee is only as strong as the host's authenticated round-1 transcript.

A signer that does not implement this BIP round-trips these fields as unknown key-value pairs (BIP-174 requires unknown pairs to be passed through) and produces an ordinary, **unprotected** signature. See [Backwards Compatibility](#backwards-compatibility).

## Backwards Compatibility

The protocol is carried entirely in PSBT key-value pairs and introduces no consensus change; anti-exfil signatures are ordinary ECDSA/Schnorr signatures and verify and confirm like any other.

* **Non-supporting signers.** A signer that does not understand these fields treats them as unknown and, per BIP-174, passes them through unchanged when re-serializing. It will produce a normal signature with a nonce of its own choosing — i.e. an **unprotected** signature. The presence of the anti-exfil fields in a PSBT does not compel a non-supporting signer to do anything.
* **Fail-closed.** A verifier that intends to rely on anti-exfil protection MUST treat a **missing or invalid** binding as failure, never as success. "No valid binding present" means "no protection," not "OK". In particular, a signature on an input for which `Q` and `rho` are unavailable, or for which `x(Q + tweak*G) != r` (ECDSA) / `!= R_x` (Schnorr), MUST be reported as unprotected/invalid by an anti-exfil-aware verifier, even though it may be a perfectly valid Bitcoin signature.

## Rationale

**Why two rounds with commitments in this order.** If the host could choose `rho` after seeing `Q`, it could grind `rho` to steer the final `R` and re-open a channel; committing to `rho` first prevents that. If the signer could choose `Q` after learning `rho`, it would regain nonce freedom; committing to `Q` first prevents that. Only with both commitments preceding both reveals is the final nonce `R = Q + tweak*G` outside either party's unilateral control.

**Why the binding is on `x(R)` only (and what that buys Taproot).** The verifier reconstructs `R = Q + tweak*G` and compares only the x-coordinate against the signature. For ECDSA the signature's `r` is already `x(R) mod n`, so this is natural. For Schnorr, BIP-340 requires `R` to have even y and will internally negate the nonce to achieve it; since `x(P) == x(-P)`, committing to `x(R)` only makes the binding check immune to that negation. This is why the Taproot `Q` is committed even-y but the verification is parity-independent.

**ECDSA `Q` natural parity vs Taproot `Q` even-y.** These are the two easiest things to get wrong. The ECDSA `signer_commitment` is a 33-byte compressed point carrying its true parity, because ECDSA verification reconstructs a full point and the tweak commits to that exact 33-byte encoding. The Taproot `signer_commitment` is 32-byte x-only and MUST be even-y (negate `q` if needed before committing), to match BIP-340's x-only world. Swapping these breaks the binding.

**Why two PSBT field families rather than one.** The disambiguating keydata differs by signature type (33-byte compressed key vs 32-byte x-only key, optionally with a 32-byte leaf hash for script path), and the `signer_commitment` value length differs (33 vs 32 bytes). A single shared keytype would require a verifier to infer the signature type out-of-band to parse the keydata and value correctly. Splitting into an ECDSA family and a Taproot family makes each field self-describing and mirrors the existing split between `PSBT_IN_PARTIAL_SIG` and `PSBT_IN_TAP_KEY_SIG`/`PSBT_IN_TAP_SCRIPT_SIG`.

**Why the Taproot key-path keydata is the x-only output key, not empty.** `PSBT_IN_TAP_KEY_SIG` has no keydata because a key-path spend has exactly one signature and one key, so the signature attaches unambiguously to the output key. The anti-exfil fields, however, can legitimately appear for multiple independent signer keys per input (e.g. multisig setups where each signer runs the protocol separately) and benefit from being explicitly keyed; using the x-only output key as keydata keeps the field symmetric with the ECDSA family and with `PSBT_IN_TAP_SCRIPT_SIG`, and removes any ambiguity if more than one signer's data is present.

**Relationship to libsecp256k1 `anti_exfil`.** Construction A is the sign-to-contract construction of the libsecp256k1-zkp `anti_exfil` (`ecdsa_s2c`) module, deployed in Blockstream Jade and BitBox02 (where it is called *anti-klepto*), and this BIP adopts its exact ECDSA wire format: the same tag strings (`s2c/ecdsa/data`, `s2c/ecdsa/point`), the same RFC 6979 derivation with `host_commitment` as extra entropy, and the same tweak layout (`Q33 || rho`). An ECDSA implementation already speaking that protocol can produce and verify Construction A bindings unchanged. What this BIP adds on top is: the Schnorr / Taproot construction (new ground — the deployed module is ECDSA-only), PSBT carriage for air-gapped operation, and stricter normative behavior than the C API (fail-closed aborts, host pinning, `rho` freshness, cross-scheme separation). Both constructions use the same tweak shape (`Q || rho`) and each scheme's own standard nonce derivation, so the two constructions are exact parallels of each other.

**Tag naming.** The ECDSA tags are final — they are the values deployed in libsecp256k1-zkp. The Schnorr tags deliberately mirror the same `s2c/<scheme>/<role>` naming scheme; since the Schnorr construction has no deployed format to stay compatible with, these values are defined by this BIP and are final as well. No placeholders remain to be resolved at number-assignment time.

## Security Considerations

* **Host commits `rho` first.** Sending `host_commitment` before learning `Q` prevents a malicious host from choosing `rho` adaptively after seeing the signer's nonce point, which would otherwise let the host steer the final `R`.
* **Signer commits `Q` before learning `rho`.** With `rho` unknown at commit time, the final nonce `R = Q + tweak*G` is unpredictable to the signer. This removes the signer's nonce freedom and with it the exfiltration channel: there is no longer any choosable, observable degree of freedom in which to encode key bits.
* **The host MUST pin the round-1 transcript.** The commit-before-reveal ordering is only enforced if the host retains the exact round-1 `host_commitment` and `Q` and rejects any changed values in the signer's final output. If the host instead reads `Q` from the PSBT the signer returns in round 2, a malicious signer can wait for `rho`, grind a fresh `q'` until `x(q'*G + tweak'*G)` (with `tweak'` computed from `q'*G` and the known `rho`) encodes key bits, write that `Q' = q'*G` into the PSBT, and produce a fully consistent signature — the binding check passes and the exfiltration channel is wide open. Pinning the round-1 values closes this completely. A third party that did not run round 1 (or lacks the host's retained transcript) cannot verify the ordering at all: for them the binding is a consistency check, not proof of protection.
* **`rho` MUST be fresh and unpredictable.** The security argument requires `rho` to be unknown to the signer at the time it commits to `Q`. If `rho` has low entropy, the signer can recover it from `host_commitment` by brute force; if `rho` was revealed in any earlier protocol run, the signer can recognize the reused `host_commitment`. In either case the signer knows `rho` before choosing `Q` and can grind `q` to steer the final nonce. The host MUST therefore generate `rho` with a cryptographically secure RNG for every new protocol instance and MUST NOT reuse it across different transactions, inputs, or signers. The only permitted reuse is the same-transaction, same-`Q` retry of the selective-abort mitigation below, which is safe because the deterministic derivation pins the entire transcript.
* **Cross-scheme nonce separation is mandatory.** If the same `(sk, digest, host_commitment)` were used to derive `q` identically for an ECDSA and a Schnorr signature, the two signatures would provide two linear equations in the two unknowns `q` and `sk`: ECDSA gives `s*(q + tweak_ec) = ±(z + r*sk)`, Schnorr gives `s' = ±(±q + tweak_sch) + e*sk`, and all tweak values are public to anyone holding `Q` and `rho`. Solving the pair recovers the private key (this is the cross-scheme nonce reuse that BIP-340's nonce guidance also warns against). A signer MUST therefore derive the Schnorr `q` with the BIP-340 nonce derivation (`host_commitment` as auxiliary data), never with the ECDSA RFC 6979 derivation, so the two schemes never share a nonce scalar.
* **Residual selective-abort channel (inherent to the protocol class).** Removing nonce freedom does not remove the signer's freedom to *refuse*. A malicious signer can attempt to leak roughly one bit per signing attempt by computing the final `R` in round 2 and aborting whenever the bit it wants to leak does not match. The primary mitigation is to make aborting worthless: on any round-2 failure the host MUST restart the protocol with **exactly the same `rho`** (and the same transaction) and MUST demand **exactly the same `signer_commitment` `Q`**. With the deterministic `q` derivation of this BIP, `q` is a pure function of `(sk, digest, host_commitment)`, so a same-`rho` retry pins the signer to the identical `Q`, the identical final nonce, and the identical signature — the signer gains nothing by aborting except denial of service. A host SHOULD only escalate to a fresh `rho` if the signer cannot be made to complete with the given `(rho, Q)` pair at all, and SHOULD treat such repeated aborts as evidence of compromise: present an alarming warning, and if it happens more than a handful of times (on the order of 20, ever, across any set of devices holding the same keys), advise the user to change signing devices and consider sweeping funds. (The 2020 analysis of this protocol class estimates >100 effective aborts are needed for a plausible key-recovery attack; aborts accumulate across device replacements but reset with independently generated new keys.)
* **`Q` MUST NEVER appear on-chain.** Only the `rho`-randomized `r` / `R_x` is published. `Q` is seen only by the trusted host (and any verifier the host shares it with). A passive on-chain observer who never sees `Q` learns nothing exfiltratable from the signatures.
* **Deterministic nonce and reuse safety.** Deterministic derivation of `q` is RECOMMENDED. A different `rho` yields a different `host_commitment`, hence a different `q`, hence a different signature. Re-running the protocol on *identical* inputs (same `sk`, `digest`, `host_commitment`) reproduces an identical signature, which is safe; what must never happen is two *different* signatures over different messages reusing the same final nonce `k`.
* **Tamper / replay binding.** The `signer_commitment` is derived from the `digest`, so it binds the transaction being signed. Any change to the transaction between rounds, a tampered `signer_commitment`, or an attempt to skip round 1 (the host cannot forge a valid `Q` without `sk`) MUST cause the signer to abort. The signer MUST verify that `host_commitment` opens to `rho` and MUST reproduce `Q` before signing.
* **Schnorr parity.** The binding is on `x(R)` only and `x(P) == x(-P)`, so BIP-340's internal even-`R` nonce negation does not break verification; `Q` is committed even-y. (See Rationale.)
* **`q` is key-equivalent — treat it like the private key.** The secret nonce `q` (equivalently the final nonce `k`) is as sensitive as the private key: `q` together with the published signature reveals the private key. For ECDSA, `d = (s*k - z) * r^{-1} mod n`; an analogous relation holds for Schnorr (`d = (s - k) * e^{-1} mod n`). Implementations MUST zeroize `q`, `k`, and any private-key copies promptly, and MUST handle `q` with the same protections as the private key in the Security model.
* **Low-S, no low-R grinding.** ECDSA signatures MUST be low-S (BIP-146). Low-R grinding MUST NOT be performed: the nonce is forced by `k = (q + tweak) mod n` and cannot be ground, so roughly half of signatures will have a high `r` and the DER encoding will be ~1 byte longer on average, with a correspondingly minor transaction-fee implication. This is an accepted cost of removing nonce freedom.

All vectors were computed by the reference generator in [`bip-antiexfil/generate-test-vectors.py`](bip-antiexfil/generate-test-vectors.py), a self-contained pure-Python secp256k1 implementation that injects the forced nonce `k = (q + tweak) mod n` into signing. Each vector is verified internally: the binding is reconstructed offline as `R = Q + tweak*G` and checked against the published `r`/`R_x`, and the signature is verified with an independent verifier. The four PSBTs in Vector 4 have additionally been confirmed to parse with the `embit` library.

Tags used: `HOST_COMMITMENT_TAG = "s2c/ecdsa/data"`, `ECDSA_TWEAK_TAG = "s2c/ecdsa/point"` (both deployed in libsecp256k1-zkp), `SCHNORR_HOST_COMMITMENT_TAG = "s2c/schnorr/data"`, `SCHNORR_TWEAK_TAG = "s2c/schnorr/point"` (defined by this BIP).
